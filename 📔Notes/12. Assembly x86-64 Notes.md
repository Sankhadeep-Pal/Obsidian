## What is Assembly?
At its absolute core, a computer processor doesn’t understand text, variables, or objects. It only understands **Machine Code**—a massive, raw stream of 1 s and 0 s (binary) or hex numbers.

**Assembly language is simply a human-readable representation of that machine code.**

---

## Where Assembly Sits in the Software Stack

Think of software development as a ladder of abstraction. The higher you go, the closer you are to human language. The lower you go, the closer you are to the physical hardware.

- **High-Level (MERN Stack / JavaScript / Python):** Highly abstract. You write `console.log("Hello")`. The code doesn't care about memory management, CPU registers, or hardware architecture.

- **Compiled Languages (C / C++ / Rust):** Closer to the metal. You manage pointers and memory, but a compiler still translates your logic into optimised machine instructions.

- **Assembly Language:** Zero abstraction. **One line of assembly converts directly into exactly one machine code instruction.** You are speaking directly to the CPU components.

- **Machine Code / Hardware:** Raw binary (`01001000 10001001...`) flowing through electrical transistors.

---

## The 1:1 Relationship (Assembly vs. Machine Code)

When you write high-level code, one line of JavaScript might turn into dozens of CPU operations. In assembly, there is a **strict 1:1 mapping**.

An **Assembler** (like `nasm` or `as`) doesn't do complex compilation or smart logic optimization. It is essentially a glorified dictionary that translates human mnemonics (like `mov` or `add`) directly into their exact binary equivalents.

| Assembly Mnemonic | What it tells the CPU                | Raw Machine Code (Hex) |
| ----------------- | ------------------------------------ | ---------------------- |
| `mov rax, 5`      | "Move the value 5 into register RAX" | `48 c7 c0 05 00 00 00` |
| `add rax, rbx`    | "Add the contents of RBX to RAX"     | `48 01 d8`             |

---

## The Ultimate Bridge: Hardware to Software

At the lowest level, your computer's CPU only understands **machine code**—millions of 1 s and 0 s arranged in specific patterns.

Writing millions of `10110000 01100001` by hand is virtually impossible for humans. **Assembly language** solves this by replacing those cryptic 1 s and 0 s with short, human-readable words called **mnemonics** (like `MOV`, `ADD`, `PUSH`, or `JMP`).

---

## How It Works: The Assembler

Because the CPU cannot directly run text like `ADD`, a utility software called an **Assembler** translates your assembly code directly into machine code.

Unlike a complex C++ or JavaScript compiler that heavily optimizes, rearranges, and rewrites your logic, an assembler has almost a **1-to-1 relationship** with machine code. One line of assembly usually equals exactly one instruction for the CPU.

---

## Anatomy of an Assembly Instruction

Every CPU architecture (like x 86 in your laptop, or ARM in your phone) has its own unique assembly language. However, the basic structure of a line of assembly usually looks like this:

```code
MOV    EAX, 42    ; Copy the number 42 into the CPU register named EAX
```

- **Mnemonic (`MOV`):** The operation to perform (Short for "Move").

- **Destination (`EAX`):** _Where_ the data goes. In this case, a **register** (a tiny, lightning-fast storage slot inside the CPU itself).

- **Source (`42`):** The data or value being used.

---

## Why You Must Learn It for Low-Level Dev

Since your goal is microcontroller programming and kernel development, assembly isn't optional—it's a superpower. Here is why:

- **Direct Hardware Control:** You manipulate CPU registers, flags, and memory addresses directly. You control the hardware, it doesn't control you.

- **Bare-Metal Bootstrapping:** When a microcontroller or PC first turns on, C or C++ environments aren't ready yet. The very first code that initialises the system registers and sets up the stack is written in assembly.

- **Reverse Engineering & Debugging:** When a kernel crashes (Kernel Panic / Blue Screen), debugging requires reading the raw assembly memory dump to see exactly which CPU instruction caused the failure.

## Assembly Core Concepts

### 1. The CPU Architecture: Architecture vs. Microarchitecture
Before diving into code, you must understand the distinction between what you _program_ and what _physically exists_.

- **ISA (Instruction Set Architecture):** This is the abstract model of the processor that you interface with (e.g., x 86_64, ARM). It defines the supported instructions, registers, and memory models. It is the "programmer's manual."

- **Microarchitecture:** This is the physical implementation of the ISA in silicon (e.g., an Intel Core i 9 vs. An AMD Ryzen). They execute the same x 86_64 assembly instructions, but their internal physical wiring, cache sizes, and transistor layouts are completely different.

### 2. Registers: The CPU's Scratchpad
Registers are ultra-fast, tiny storage locations built directly inside the CPU core. Accessing RAM takes hundreds of clock cycles; accessing a register takes less than one. In x 86_64, general-purpose registers are **64 bits (8 bytes)** wide.

#### The General-Purpose Registers (GPRs)
You have 16 primary general-purpose registers. While they can hold any data, historical conventions give them specific roles:

- **`rax` (Accumulator):** Used for arithmetic and automatically holds the return value of functions.

- **`rbx` (Base):** Historically used as a pointer to data.

- **`rcx` (Counter):** Automatically used as a loop counter by certain instructions.

- **`rdx` (Data):** Used in multiplication/division and for I/O operations.

- **`rsi` (Source Index):** Points to the source stream in string/memory operations.

- **`rdi` (Destination Index):** Points to the destination stream; also used to pass the 1 st argument to functions.

- **`rsp` (Stack Pointer):** Points to the very top of the Stack in memory. _Do not use for math._

- **`rbp` (Base/Frame Pointer):** Points to the base of the current function's stack frame.

- **`r8` to `r15`:** Purely general-purpose registers added in the 64-bit extension.

#### Register Subdivisions (The Anatomy of RAX)
You don't always need all 64 bits. A major feature of x 86_64 is backward compatibility. You can access smaller portions of the exact same register:

- **`rax`:** The full 64 bits (8 bytes)

- **`eax`:** The lower 32 bits (4 bytes)

- **`ax`:** The lower 16 bits (2 bytes)

- **`al`:** The lower 8 bits (1 byte)

- **`ah`:** The upper 8 bits of the `ax` register (rarely used today)

```
+---------------------------------------------------------------+
|                           RAX (64 bits / 8 bytes)             |
+-------------------------------+-------------------------------+
                                |          EAX (32 bits)        |
                                +---------------+---------------+
                                                |   AX (16 bits)|
                                                +-------+-------+
                                                |AH(8b) |AL(8b) |
                                                +-------+-------+
```

> [!WARNING] **Crucial Rule:** Writing to a 32-bit register (like `eax`) automatically clears (zeroes out) the upper 32 bits of the parent 64-bit register (`rax`). Writing to 16-bit or 8-bit registers does _not_ clear the upper bits.

### 3. Memory Layout: RAM vs. Registers
The CPU cannot run code or manipulate data directly inside your RAM. It must follow the **Fetch-Decode-Execute** cycle.

1. **Fetch:** Read the instruction from RAM (at the address pointed to by `rip`).

2. **Decode:** The CPU's control unit figures out what the instruction means (`mov`, `add`, etc.).

3. **Execute:** The Arithmetic Logic Unit (ALU) performs the operation, using registers.

#### Memory Addressing Mode Syntax (`[]`)
When you see brackets, you are dealing with pointers.

- `mov rax, rbx` → Copy the _value_ inside `rbx` into `rax`.

- `mov rax, [rbx]` → Look at the value inside `rbx`, treat that value as an address in RAM, go to that address, and copy whatever data is sitting there into `rax`.

### 4. The Flags Register (`rflags`)

The CPU has a special status register called `rflags`. Each bit in this register acts as a tiny 1-bit boolean switch (a "flag"). Whenever you perform an arithmetic operation (`add`, `sub`, `dec`), the CPU automatically sets or clears these flags based on the mathematical result.

- **ZF (Zero Flag):** Set to `1` if the result of the last operation was exactly `0`.

- **SF (Sign Flag):** Set to `1` if the result was negative.

- **CF (Carry Flag):** Set to `1` if an unsigned math operation overflowed (e.g., adding 1 to the maximum possible number).

- **OF (Overflow Flag):** Set to `1` if a _signed_ math operation overflowed into the sign bit.

You don't modify these directly. Instead, conditional jump instructions (like `jnz` - Jump if Not Zero, or `je` - Jump if Equal) look at these flags to decide whether to change the `rip` register and branch your code.

### 5. Endianness: How Memory is Ordered

As briefly mentioned before, x 86_64 is **Little-Endian**.

If you have a 32-bit hex number `0x12345678`, it is made of 4 bytes: `12`, `34`, `56`, and `78`.

- **Big-Endian (Human Readable):** Stored sequentially: `12 34 56 78`

- **Little-Endian (x 86_64 Processor):** Stored least-significant byte first: `78 56 34 12`

## Assembly Arithmetic Operations

### The Two-Operand Rule
Unlike high-level languages where you can write `x = y + z`, x 86_64 arithmetic instructions typically use **two operands**.

- Syntax: `INSTRUCTION destination, source`

- The `destination` operand plays a double role: it acts as one of the inputs _and_ the location where the final result is saved.

- **Core Limitation:** You cannot perform arithmetic directly from one memory location to another memory location (e.g., `add [rax], [rbx]` is invalid). At least one operand must be a register.

### Fundamental Arithmetic Instructions

#### 1. `ADD` (Addition)
Adds the source to the destination and stores the result in the destination.

- **Syntax:** `add dest, src` → dest=dest+src

- **Flags Affected:** ZF, SF, CF, OF (Updates all major status flags).

```CODE
mov rax, 5
add rax, 10      # rax is now 15
```

#### 2. `SUB` (Subtraction)
Subtracts the source from the destination and stores the result in the destination.

- **Syntax:** `sub dest, src` → dest=dest−src

- **Flags Affected:** ZF, SF, CF, OF.

```code
mov rbx, 20
sub rbx, 8       # rbx is now 12
```

#### 3. `INC` and `DEC` (Increment / Decrement)
Adds or subtracts exactly `1` from the operand. These instructions are optimized to take up less space in machine code than a full `add` or `sub` instruction.

- **Syntax:** `inc dest` (dest=dest+1) or `dec dest` (dest=dest−1)

- **Flags Affected:** ZF, SF, OF.

- ⚠️ **Crucial Gotcha:** `inc` and `dec` **do not modify the Carry Flag (CF)**. This becomes highly critical when dealing with multi-precision math or specific loop structures.

```assembly
mov rcx, 1
inc rcx          # rcx is now 2
dec rcx          # rcx is back to 1
```

#### Advanced: Multiplication and Division
Multiplication and division on x 86_64 are **implicit**. They do not follow the clean `dest, src` rule because the results can quickly become too large to fit in a single 64-bit register.

###### 1. `MUL` / `IMUL` (Multiplication)

- `mul` is for unsigned integers; `imul` is for signed integers.

- **How it works:** You only provide _one_ explicit operand (the source). The CPU assumes the other multiplier is **always** inside `rax`.

- **The Result Split:** Multiplying two 64-bit numbers can result in a 128-bit number. To handle this, the CPU automatically splits the result across two registers: the upper 64 bits go to `rdx`, and the lower 64 bits go to `rax`.

```code
Mov rax, 5       # Implicit factor must be in rax
Mov rbx, 10      # Second factor
Mul rbx          # Computes rax * rbx -> Result is 50
                 # Lower 64 bits (50) are in rax. Upper 64 bits (0) are in rdx.
```

##### 2. `DIV` / `IDIV` (Division)

- `div` is for unsigned integers; `idiv` is for signed integers.

- **How it works:** Like multiplication, it relies on implicit registers. You pass it a divisor. The CPU expects the dividend (the number being divided) to be a 128-bit value spanning across `rdx:rax`.

- **The Result Split:** After execution, the CPU splits the output:
    
    - `rax` holds the **Quotient** (the result of the division).
    
    - `rdx` holds the **Remainder** (the modulo).

```code
# To divide 21 by 5:
Mov rax, 21      # Lower part of dividend
Mov rdx, 0       # Clear rdx! (Crucial, or the CPU thinks the number is massive)
Mov rbx, 5       # Divisor
Div rbx          # Divides rdx: rax by rbx
                 # rax now holds quotient: 4
                 # rdx now holds remainder: 1
```

#### Arithmetic Sign Extension (`cqo`)
When performing signed division (`idiv`), you cannot simply clear `rdx` with `0` if your number in `rax` is negative. Doing so would destroy the negative sign bit.

To fix this, x 86_64 introduces `cqo` (**Convert Quadword to Octaword**). It looks at the sign bit of `rax` and copies that bit across every single bit of `rdx` (sign extension), safely preparing `rdx:rax` for division.

```code
Mov rax, -21
Cqo              # Automatically populates rdx with 1 s to maintain the negative sign
Mov rbx, 5
Idiv rbx         # rax = -4, rdx = -1
```

## Clobbering
> [!NOTE] Definition
> **Clobbering** refers to the overwriting of data inside a register or memory location as a side-effect of an instruction. A register is said to be "clobbered" if its previous value is destroyed and replaced with a new value.

This happens primarily because x86_64 arithmetic instructions use a **two-operand system** where the destination operand plays a dual role: it is both an input value *and* the output location.

### The Classic Example:

```assembly
mov rax, 10
mov rbx, 5

add rax, rbx     # Mathematical Operation: rax = rax + rbx

```

* **What happens to `rbx`?** Nothing. It still holds `5`.
* **What happens to `rax`?** Its original value (`10`) is completely wiped out and replaced with `15`. **`rax` has been clobbered.**

If you needed that original number `10` for a calculation later in your program, you are out of luck. It is gone forever unless you saved it somewhere else first.

### Types of Clobbering

#### 1. Arithmetic Clobbering (Destination Overwrite)
As shown above, the destination register of an `add`, `sub`, `imul`, `inc`, or `dec` instruction is automatically clobbered by the result of the operation.

#### 2. Implicit Hardware Clobbering (The Hidden Trap)
Some instructions clobber registers that aren't even listed in the line of code you wrote. As you learned with division, the `idiv` instruction doesn't just calculate a result—it aggressively overwrites specific registers.

```assembly
# Assume rax = 100, rdx = 9999 (some important data you need later)
mov rbx, 10
cqo               # Clobbers rdx! It overwrites 9999 with sign-extension bits.
idiv rbx          # Clobbers rax (gets quotient) AND clobbers rdx again (gets remainder)

```

Even though you only typed `idiv rbx`, **both `rax` and `rdx` were completely clobbered** by the hardware design.

#### 3. Function/System Call Clobbering
When you transition to writing bigger programs and start using `syscall` (to talk to the Linux kernel) or calling C functions, you enter a dangerous clobbering zone.

The Operating System or the function you call will use the CPU registers to do its own work. According to the standard **x86_64 System V AMD64 ABI** (the low-level rules of engagement), when you make a function call:

* The registers **`rax`**, **`rcx`**, **`rdx`**, **`rsi`**, **`rdi`**, **`r8`**, **`r9`**, **`r10`**, and **`r11`** are considered **caller-saved**.
* This means the function you are calling is legally allowed to clobber them without warning. If you leave data in them, expect it to be ruined when the function returns.

### How Low-Level Programmers Prevent Accidental Clobbering
To prevent losing data to clobbering, you must preserve your values. There are two primary ways to do this:

#### Strategy A: Register Shuffling (Scratchpads)
Before running an operation that will clobber a register, copy the vital data into an unused "scratchpad" register.

```assembly
mov rax, 10      # Vital data
mov rbx, 5

mov rcx, rax     # Save a backup copy of rax into rcx
add rax, rbx     # rax is clobbered (now 15)
                 # But our original '10' is still safe in rcx!

```

#### Strategy B: Using the Stack (Push & Pop)
If you run out of free registers, you can temporarily save your data onto the system RAM stack using `push`, and restore it later using `pop`.

```assembly
push rax         # Copies the current value of rax safely onto the Stack memory
add rax, rbx     # rax is clobbered with the math result
# ... do some work with the result ...
pop rax          # Restores the original pre-math value back into rax!

```

### Summary
Think of clobbering like working on a whiteboard with a single marker and eraser. If you want to calculate something new, you often have to erase what was previously written in that space. As an assembly programmer, tracking *which* registers are currently holding "clean, vital data" versus "clobbered, disposable data" is 90% of the mental battle.

## Memory Handling & Architecture

### Memory Segments & CPU Instructions

- `.text`: Tells the CPU/OS that this section contains executable code. The CPU loads these instructions into memory to execute them.

- `.data`: Instructs the CPU/OS to allocate space in RAM for static variables/data storage, not for execution.
 
- `_start:`: The global entry point where execution begins.    

### Pointers vs. Values (`mov` vs. `lea`)
Using `.intel_syntax noprefix` changes how we interact with memory labels:

- `mov rbx, reg16` or `lea rcx, [reg16]`: Both load the **address (pointer)** of `reg16` into the register.

- `mov rax, [reg16]`: Dereferences the pointer. It grabs the actual **data value** stored _at_ the address of `reg16`.

### Data Sizing Reference Table

|**Directive**|**Type**|**Size in Bits**|**Size in Bytes**|
|---|---|---|---|
| `.byte` |Byte|8 bits|1 byte|
| `.word` |Word|16 bits|2 bytes|
| `.long` or `.double` |Double Word|32 bits|4 bytes|
| `.quad` |Quad Word|64 bits|8 bytes|

- `.skip 512, 0xff`: Allocates a continuous block of 512 bytes, initializing every single byte to `0xff`.

## Hello World & System Calls

### Conceptual Overview: High-Level vs. Low-Level
In high-level languages like C, a simple `printf("Hello World");` hides a massive amount of complexity. Under the hood, the standard library and the Operating System kernel carry out a sequence of precise steps:

1. **Format** the string (handling specifiers like `%d`, `%s`).

2. **Identify the Operation:** Tell the kernel we want to _write_ data.

3. **Identify the Destination:** Tell the kernel _where_ to write (e.g., the Terminal/Stdout).

4. **Locate the Data:** Provide the _memory address_ of the string.

5. **Determine the Size:** Provide the _exact length_ of the data in bytes.

In high-level languages, wrapper functions (`printf`, `write`) handle this. In Assembly, **we must manually populate CPU registers with these arguments before triggering a kernel interruption.**

### The System Call (Syscall) Blueprint

When you execute the `syscall` instruction, the CPU transitions from user mode to kernel mode. The kernel automatically looks at specific hardware registers to figure out what to do.

### The 64-bit Linux Syscall Register Mapping

| **Register** | **Purpose / Role**                      | **write (1)**     | **exit (60)**           |
| ------------ | --------------------------------------- | ----------------- | ----------------------- |
| `rax`        | **System Call ID** (The Operation Code) | `1`               | `60`                    |
| `rdi`        | **Argument 1:** Where/Target            | `1` (Stdout)      | `99` or `0` (Exit Code) |
| `rsi`        | **Argument 2:** Data Memory Address     | Pointer to String | _Not Used_              |
| `rdx`        | **Argument 3:** Data Size (Bytes)       | Length of String  | _Not Used_              |
| `r10`        | **Argument 4:** Additional arguments    | _Not Used_        | _Not Used_              |
| `r8`         | **Argument 5:** Additional arguments    | _Not Used_        | _Not Used_              |
| `r9`         | **Argument 6:** Additional arguments    | _Not Used_        | _Not Used_              |

> ⚠️ **Crucial Side Effect Note:** When a `syscall` executes, the kernel often overwrites the `rax` register with its **return value**. For a `write` call, `rax` will contain the number of bytes successfully written. Always re-populate `rax` before your next syscall!

### Memory Directives & Dynamic Math

#### 1. Directives

- `.intel_syntax noprefix`: Switches the assembler to Intel syntax (Destination, Source) and removes the requirement of putting `%` before register names.

- `.global _start`: Declares the entry point symbol visible to the linker.

- `.text`: The memory segment where the executable CPU instructions live (Read-Only).

- `.data`: The memory segment where initialized variables and data live (Read-Write).

#### 2. The Location Counter (`.`) Pointer Trick
Instead of hard-coding string lengths, we use assembler math:

```asm
string1: .ascii "Sankhadeep"
str1Len = . - string1
```

- `.` represents the **Current Location Counter** (the memory address immediately _after_ the last character of the string).

- `string1` represents the **Base Address** (where the string started).

- `.` minus `string1` gives us the exact delta bytes safely and dynamically.
